IMPORTANT DEPLOYMENT NOTE (ACCOUNT CREATION FIX):
The browser publishable key is NOT sufficient for KETS backend registration/payment writes when
Supabase Row Level Security is enabled. Render must have SUPABASE_URL plus either
SUPABASE_SECRET_KEY (preferred) or SUPABASE_SERVICE_ROLE_KEY. Keep that key server-side only.
Run KETS_SUPABASE_REPAIR_ALL.sql once in Supabase SQL Editor.

KETS FINAL SIGN-IN 500 FIX
==========================

Root cause fixed:
The normal /api/auth/login handler queried Supabase BEFORE checking the
KETS developer credentials. If Supabase/RLS rejected that query, the developer
login returned HTTP 500 even though developer access is independent of the
users table.

Changes in this package:
1. Developer credentials are checked first.
2. Developer login therefore works without a users-table lookup.
3. Normal-user database failures return HTTP 503 instead of an unhandled 500.
4. Supabase publishable keys remain on the `apikey` header only.
5. Render declares the developer username/password as private environment vars.
6. /api/auth/me already recognizes the developer token without a database query.

RENDER ENVIRONMENT
------------------
Set these in Render -> KETS service -> Environment:

SUPABASE_URL
SUPABASE_PUBLISHABLE_KEY
KETS_DEVELOPER_USERNAME
KETS_DEVELOPER_PASSWORD

KETS_SESSION_SECRET is generated by render.yaml.

DEPLOY
------
1. Replace the deployed project files with this package.
2. Commit/push to the GitHub repository connected to Render, OR upload the
   project to the deployment source you use.
3. Trigger a fresh Render deploy.
4. Confirm /api/health returns OK.
5. Open the KETS Sign in page.
6. Enter the developer username/email and developer password stored in Render.
7. The normal Sign in form should now authenticate the developer account for free.

IMPORTANT
---------
Do not put the developer password in HTML, JavaScript, GitHub, SQL files,
or screenshots. If the developer password has ever been exposed, rotate it
in Render before deploying.
