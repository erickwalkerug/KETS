KETS ACCOUNT CREATION REPAIR — DEPLOY THIS VERSION

What was repaired:
- Backend accepts SUPABASE_SECRET_KEY or the legacy LEGACY_SERVICE_ROLE_KEY_NOT_USED.
- Render configuration now declares both server-key variables consistently.
- Registration failures return safe, useful diagnostics instead of a generic HTTP 500.
- Browser "Failed to fetch" is converted to a clear server-connectivity message.
- Added /api/diagnostics for checking whether the Render service has a server-only DB key.
- Added KETS_SUPABASE_REPAIR_ALL.sql to repair older/partial Supabase schemas without deleting data.

IMPORTANT:
1. In Supabase SQL Editor, run KETS_SUPABASE_REPAIR_ALL.sql.
2. In Render Environment, set:
   SUPABASE_URL=https://YOUR-PROJECT.supabase.co
   SUPABASE_SECRET_KEY=YOUR_SERVER-ONLY-SUPABASE-SECRET-KEY
   KETS_SESSION_SECRET=YOUR-STABLE-RANDOM-SECRET (or let render.yaml generate it)
3. If your project only has the legacy service-role JWT, set LEGACY_SERVICE_ROLE_KEY_NOT_USED instead.
4. Do NOT put the secret/service-role key into app.js, index.html, Android code, or GitHub.
5. Deploy/redeploy the KETS Render service.
6. Open /api/health. It should report database_configured=true and database_mode=server-key.
7. Create a brand-new account.

If /api/health says database_configured=false, the Render environment is still missing the server key.
If registration says DB_SCHEMA_MISMATCH, run the SQL repair file and redeploy/retry.
